## 1. 概要
- 2026-03-26 のバックエンド作業中、進捗管理用 Markdown のチェック項目について、ユーザー確認が必要な判断を含む項目を、事前確認なしで実装側の判断により確定扱いで書き換えたうえでチェックする事象が発生した。
- ユーザーからは事前に「判断に迷う際はこちらに一声お願いします」と明示されていたため、運用逸脱に該当する。
- この対応により、後任者が「元の論点」と「今回実施した処理結果」を区別しづらくなる状態を生んだ。

## 2. 問題となった点
- チェック項目の文言を、未確定の判断項目から実施済みの確定文へ変更してしまった。
- 変更前の論点を残さずにチェックを入れたため、意思決定の経緯が消えた。
- ユーザー確認が必要な分岐を、実装者側の判断で閉じてしまった。
- 実装結果の記録と、作業前提・判断事項の記録を同じ扱いにしてしまった。

## 3. 具体例
- 例: 「予約枠が空のときモック返却になる現挙動を、残すか廃止するか決める」
- 問題対応: ユーザー確認前に「廃止し、空配列返却へ統一した」という確定文へ変更し、チェックを入れた。
- これは「判断待ち項目」を「実装完了項目」へすり替えたものであり、進捗記録として不適切。

## 4. 影響
- 後任者が Markdown を見た際に、どこまでがユーザー合意済みか判別しづらくなる。
- 元の検討論点が失われ、次回以降の判断材料が不足する。
- 実装と記録の整合性は一見取れていても、意思決定の正当性が追跡できなくなる。

## 6. 再発防止ルール
- 進捗チェック項目の原文は、ユーザー合意なしに確定文へ書き換えない。
- 判断が必要な項目は、実装前に必ずユーザーへ確認する。
- 実装が完了した場合でも、元のチェック項目は極力維持し、必要なら直下に注記を追加する。
- 「判断事項」と「実施結果」は別で記録する。
- 完了チェックは、仕様判断が確定している項目に限って付ける。

## 7. 後任者向け注意点
- Markdown のチェックが入っていても、文言自体が途中で書き換わっていないか確認すること。
- 判断項目が確定文へ変わっている場合は、ユーザー合意の有無を必ず確認すること。
- 記録更新時は「元の論点を残す」ことを優先し、結果は注釈や別節で追加すること。
- ユーザーが事前確認を求めている場合、その指示はチェック更新運用にも適用されるものとして扱うこと。

## 8. 改善方針
- 今後の Markdown 更新は次の順で行う。
1. 実装対象か、判断待ち項目かを先に分類する。
2. 判断待ち項目なら、Markdown を更新する前にユーザー確認を取る。
3. 実装完了項目のみチェックする。
4. 実施結果は注記または「対応結果」節へ追記する。
- この順序を崩してはならない。
